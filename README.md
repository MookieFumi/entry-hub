Room booking API used as the demo project for the blog series about Minimal APIs, OpenAPI and Aspire.
Each post links to the code of the pull request that backs it.

The domain is room booking: rooms, bookings with business rules, JWT roles and a live occupancy stream.
It grows pull request by pull request, one feature per post.

## Layout

```text
src/
  EntryHub.slnx              solution (slnx format)
  Directory.Build.props      shared build properties and quality rules
  Directory.Packages.props   Central Package Management: one version per package
  EntryHub.Api/              Minimal API organized by vertical slices (Features/V1/...)
  EntryHub.Reminders/        worker that reminds organizers shortly before their booking starts
  EntryHub.AppHost/          Aspire AppHost: PostgreSQL, the API, the reminders service and the dashboard
  EntryHub.ServiceDefaults/  telemetry, health checks and resilience shared by the services
  tests/EntryHub.Api.Tests/  unit, handler and endpoint tests
  tests/EntryHub.AppHost.Tests/  tests that start the whole system with Aspire (need containers)
deploy/k8s/                  Helm chart generated by `aspire publish` (scripts/publish-k8s.sh)
.github/                     workflows, composite governance action, Dependabot, CODEOWNERS
.husky/                      Git hook that validates Conventional Commits
GitVersion.yml               semantic version derived from tags and history
```

Every feature follows the same slice shape: a request, a handler that holds the logic and an endpoint that only
delegates to the handler. See `src/EntryHub.Api/Features/V1/Health/GetHealth` for the smallest example.

## API v1

Everything except `health` needs a JWT Bearer token. There are two roles: `Employee` (books and cancels their own
bookings, reads rooms) and `Facilities` (also creates rooms and cancels any booking).

| Method and route | Slice | Who | Notes |
|---|---|---|---|
| `GET /api/v1/health` | `Health/GetHealth` | anyone | 200, or 503 when PostgreSQL does not answer |
| `POST /api/v1/rooms` | `Rooms/CreateRoom` | Facilities | 201, 400 on a bad body, 409 when the name is taken |
| `GET /api/v1/rooms/{id}` | `Rooms/GetRoom` | any role | 200 or 404 |
| `GET /api/v1/rooms` | `Rooms/ListRooms` | any role | filters `floor` and `minCapacity`, paging with `page` and `pageSize` |
| `GET /api/v1/rooms/{id}/occupancy` | `Rooms/StreamRoomOccupancy` | any role | Server-Sent Events; free or occupied every 5 seconds |
| `POST /api/v1/bookings` | `Bookings/CreateBooking` | any role | 201, 400 bad body, 422 broken rule, 409 slot taken |
| `GET /api/v1/bookings/{id}` | `Bookings/GetBooking` | owner or Facilities | 200, 403 or 404 |
| `GET /api/v1/bookings/mine` | `Bookings/ListMyBookings` | any role | paged; `includeCancelled=true` to see cancelled ones |
| `POST /api/v1/bookings/{id}/cancel` | `Bookings/CancelBooking` | owner or Facilities | 204; 422 inside the notice period for Employees |

### Errors

- **400**: the body has the wrong shape (validation built into .NET, `AddValidation`). The response lists the fields.
- **422**: the body is fine but a business rule fails. The `violations` array has a stable `code` per rule.
- **409**: the room is already booked. The database decides, through an exclusion constraint, not the C# code.
- **503**: PostgreSQL did not answer. `DatabaseUnavailableHandler`, an `IExceptionHandler`, adds `Retry-After: 5`.
- **500**: any other exception. The client gets a generic problem details with a `traceId`; the stack trace stays in
  the logs.

Every error body is `application/problem+json` (`AddProblemDetails()` plus `UseExceptionHandler()`).

### Business rules

They live in `BookingRulesOptions` and can be changed in the `BookingRules` configuration section:
15 minutes to 4 hours in 15-minute steps, Monday to Friday from 08:00 to 20:00 in the office time zone
(`Europe/Madrid`), starting between 15 minutes and 90 days from now, cancellable until 15 minutes before the start
(Facilities at any time), and at most 5 active bookings per Employee (Facilities has no limit).

## Run it locally

Requirements: the .NET 10 SDK and a container runtime (Docker Desktop, Podman or similar).

```bash
cd src
dotnet run --project EntryHub.AppHost
```

The AppHost starts a PostgreSQL container (its data lives in a volume, so it survives restarts), waits for it, then
starts the API with the connection string already injected. It prints the URL of the Aspire dashboard
(http://localhost:15257 with the default profile), where you see the resources, their logs, traces and metrics. The
API listens on http://localhost:5178:

```bash
curl http://localhost:5178/api/v1/health
```

With the [Aspire CLI](https://aspire.dev/get-started/install-cli/) installed, `aspire run` from the repository root does
the same.

The reminders service starts after the API (the API creates the schema) and looks every 30 seconds for confirmed
bookings that start within 15 minutes. Each one produces a log line, "Reminder for ana: ... starts at ...", that you
see in the dashboard under the `reminders` resource. Both values are settings under `Reminders` (`LeadTime`,
`PollInterval`). A booking is reminded once, even with several copies of the service running.

The dashboard also lists a `scalar-api-reference` resource: one API reference for the services of the application that
publish an OpenAPI document, which today is only the API.

The API serves `/health` and `/alive` in every environment. They are the probes of the platform, and they are not the
same as `GET /api/v1/health`:

| Endpoint | For | Answers | Checks |
|---|---|---|---|
| `/health` | Kubernetes readiness, the AppHost | plain text `Healthy` or `Unhealthy`, 200 or 503 | every health check, PostgreSQL included |
| `/alive` | Kubernetes liveness | plain text, 200 or 503 | only that the process responds |
| `GET /api/v1/health` | clients | JSON, 200 or 503 | PostgreSQL, part of the versioned contract |

Readiness and liveness are separate on purpose: when PostgreSQL goes down the pods stop receiving traffic (`/health`)
but are not restarted (`/alive`), which would not fix the database. The three appear in the OpenAPI document, the
probes under the `Probes` tag. Do not route `/health` or `/alive` through an ingress.

### Get a token

Tokens for local development come from the .NET SDK. The signing key stays in your user secrets, so nothing secret
is in the repository.

```bash
cd src/EntryHub.Api
dotnet user-jwts create --role Employee --name ana        # prints the token
dotnet user-jwts create --role Facilities --name fran
curl -H "Authorization: Bearer <token>" http://localhost:5178/api/v1/rooms
```

In Development the API applies the EF Core migrations on startup. To add one after changing the model:

```bash
cd src
dotnet tool restore
dotnet dotnet-ef migrations add <Name> --project EntryHub.Api --output-dir Data/Migrations
```

There is no connection string in the repository: the AppHost injects it. Running `EntryHub.Api` on its own needs
`ConnectionStrings__EntryHub` pointing to any PostgreSQL.

## API documentation and contract

In Development the API serves an interactive page at `/scalar/v1` (Scalar, bundled with the app, no CDN) and the
OpenAPI 3.1 document at `/openapi/v1.json` and `/openapi/v1.yaml`. Authorize with a token from `dotnet user-jwts`
(see above) using the lock button.

Outside Development the interactive page does not exist and the document needs a token with the `Facilities` role,
so the contract is never public by accident. Open it to everyone on purpose by removing `RequireAuthorization` in
`Documentation/OpenApiExtensions.cs`.

The page carries the EntryHub logo (`docs/logo.svg`) and brand colors, set in `Documentation/ScalarBranding.cs`. The
static docs of the release (`docs/index.html`) repeat the same header and CSS, so change both together.

The contract is also generated at build time into `contracts/EntryHub.Api.json` and committed. CI fails if an
endpoint changes and that file does not, so every API change shows up in the pull request diff.

To update it after changing an endpoint, build and commit the file:

```bash
cd src
dotnet build        # rewrites ../contracts/EntryHub.Api.json from the code
git add ../contracts/EntryHub.Api.json
```

The contract test (`Documentation/ContractTests.cs`) checks the other direction: it calls the running API and validates
each response against the schema the contract declares for that operation, so an answer that drifts from the contract
fails the build. It covers successful responses and the errors the contract declares: 400, 404, the 409 of a repeated
room name or an overlapping booking, and the 422 of a booking that breaks the rules, with its `violations`. An endpoint
declares an error that its return type cannot describe with `ProducesProblem` or `Produces<T>`; an answer whose status
the contract does not declare fails the test too.

The endpoints with a validated body declare the 400 of the built-in validation with `ProducesValidationProblem()`, and
the contract test checks it too. The 500 and 503 are not declared per operation: any endpoint can answer them.

Every pull request also compares its contract with the one on the base branch (`.github/workflows/contract.yml`, with
[oasdiff](https://github.com/oasdiff/oasdiff)). The job summary lists every change, and a change that breaks existing
clients, such as a removed or renamed response field or a new required parameter, fails the check unless the pull
request title marks it as breaking with `!` (for example `feat(rooms)!: rename floor to level`). With `!` the merge
also bumps the major version.

## Deploy to Kubernetes

The AppHost also describes the application for a cluster. `aspire publish` turns that model into a Helm chart, and the
result is committed in `deploy/k8s` so a change to the model shows up in the pull request:

```bash
scripts/publish-k8s.sh      # regenerates deploy/k8s; CI fails if the committed chart is out of date
```

What the chart contains, and what it leaves for you:

- The API, the reminders service and PostgreSQL. The Aspire dashboard and the Scalar reference are only for running
  locally, so they are not in the chart.
- A `postgres-data` PersistentVolumeClaim (5Gi) mounted by PostgreSQL, so the data survives restarts. The storage
  class is the cluster default.
- Readiness (`/health`) and liveness (`/alive`) probes on the API.
- `Database__MigrateOnStartup=true` on the API. The PostgreSQL container starts empty, so the API creates the database
  and applies the migrations when it starts. EF Core takes a database lock while it migrates, so replicas starting at
  the same time are safe. Until PostgreSQL accepts connections the API fails to start and Kubernetes restarts it.
- Nothing sensitive. Passwords and the JWT signing key are empty entries in `values.yaml` (`secrets.*`), and the
  issuer and audience are empty entries under `config.api`: pass them when you install, never commit them.
- Image names (`parameters.api.api_image`, `parameters.reminders.reminders_image`) that you set to images you have
  built and pushed. There is no ingress either: add the one your cluster uses.

```bash
helm install entry-hub deploy/k8s \
  --set parameters.api.api_image=ghcr.io/you/entry-hub-api:1.0.0 \
  --set parameters.reminders.reminders_image=ghcr.io/you/entry-hub-reminders:1.0.0 \
  --set secrets.postgres.postgres_password=... \
  --set secrets.api.postgres_password=... --set secrets.reminders.postgres_password=... \
  --set secrets.api.jwt_signing_key=... \
  --set config.api.jwt_issuer=... --set config.api.jwt_audience=...
```

`Aspire.Hosting.Kubernetes` is still a preview package, so the shape of the chart can change between versions.

### What installing the chart taught us

CI checked for a long time that the committed chart was up to date, but nothing installed it. The first installs found
three problems that reading it did not:

| Problem | What you see | Fix |
|---|---|---|
| The publisher writes the probe scheme in lower case | `helm install` fails: `httpGet.scheme: Unsupported value: "http"` | `PublishAsKubernetesService` in the AppHost upper-cases it, so the chart stays fully generated. Remove it once the publisher writes `HTTP` |
| Nothing creates the database | The API cannot start because the `entryhub` database does not exist. Locally Aspire creates it and the API migrates only in Development | `Database__MigrateOnStartup=true`, set by the AppHost in publish mode only (see the list above) |
| `helm --wait` reports a broken API as deployed | `STATUS: deployed` while the API pod is in `CrashLoopBackOff` | Wait for the pods with `kubectl wait --for condition=Ready`. The generated Deployments run one replica with `maxUnavailable: 1`, so for Helm zero ready pods count as ready |

That last setting matters beyond CI: during a rolling update, Kubernetes may stop the only API pod before the new one
is ready. With a single replica, expect a short gap in service on every upgrade, or customize the strategy with
`PublishAsKubernetesService` before relying on it.

On a fresh install the API usually restarts once or twice: it exits while PostgreSQL is still initializing, and
Kubernetes starts it again until the migration succeeds.

The `kubernetes` job of CI installs the chart in a [kind](https://kind.sigs.k8s.io/) cluster on every pull request.
It builds both images with `dotnet publish -t:PublishContainer`, installs the chart with generated secrets, creates a
room through the API and waits for the reminders service to remind a booking. With Docker, kind, kubectl and helm
installed, the same check runs locally:

```bash
scripts/test-k8s.sh         # creates the kind cluster "entry-hub" if it does not exist
kind delete cluster --name entry-hub
```

## Releases

Push a tag such as `v1.0.0` and the `release` workflow creates a GitHub Release with the contract attached
(`openapi-v1.json`) and publishes the static docs of that version to GitHub Pages. Pages only ever shows the latest
release (https://mookiefumi.github.io/entry-hub/); older contracts stay attached to their releases. Enable it once in Settings > Pages, source GitHub Actions.

## Tests

```bash
cd src
dotnet test
```

Each slice is tested in three layers: pure logic (no I/O), the handler against PostgreSQL, and the endpoint through
`WebApplicationFactory`. The tests apply the migrations themselves before they touch the database.

Handler and endpoint tests need a PostgreSQL. By default they look for one on `localhost:5432` with the user,
password and database `entryhub`, for example:

```bash
docker run -d --name entryhub-test-db -p 5432:5432 -e POSTGRES_USER=entryhub -e POSTGRES_PASSWORD=entryhub \
  -e POSTGRES_DB=entryhub postgres:17-alpine
```

Set `ENTRYHUB_TEST_CONNECTION` to point them somewhere else (CI does this with a service container).

The tests in `tests/EntryHub.AppHost.Tests` start the whole system the way the AppHost does (PostgreSQL in a
container, the API and the reminders service), so they need a container runtime and no PostgreSQL of your own. They
carry the trait `Category=Aspire`, and the `build` job leaves them out because the `aspire` job runs them:

```bash
dotnet test tests/EntryHub.AppHost.Tests              # only the whole-system tests
dotnet test --filter "Category!=Aspire"               # everything else
```

## What CI reports on each pull request

Every run of the `ci` workflow writes a report to its summary page, and on pull requests it keeps a single
comment up to date (it is edited on each push, never duplicated):

- **Version:** what GitVersion calculates for that branch, so a `feat` or a `fix` shows its effect before the merge.
- **Tests:** total, passed, failed and skipped, and the name of every failing test.
- **Coverage:** line and branch coverage of `EntryHub.Api` and a table per class. Generated EF Core migrations are
  left out (see `src/tests/coverage.runsettings`).

The coverage comes from `coverlet.collector` and the report from ReportGenerator, both open source and run inside the
workflow, so no external service or token is needed. A coverage badge would need one (Codecov or a gist); it is not
set up.

To get the same numbers locally:

```bash
cd src
dotnet test --settings tests/coverage.runsettings --collect:"XPlat Code Coverage" --results-directory ../TestResults
dotnet tool restore
dotnet reportgenerator "-reports:../TestResults/**/coverage.cobertura.xml" "-targetdir:../TestResults/report" "-reporttypes:Html"
```

## Governance

| Rule | Where |
| --- | --- |
| Common properties and analyzers in one place | `src/Directory.Build.props`, `src/.editorconfig` |
| One version per package, locked restore | `src/Directory.Packages.props`, `packages.lock.json` files |
| Conventional Commits | `.husky/` (local hook), `.github/workflows/pr-title.yml` (PR title) |
| Semantic versioning | `GitVersion.yml`, `.config/dotnet-tools.json` |
| Build, format, vulnerabilities and tests on every PR | `.github/workflows/ci.yml`, `.github/actions/net-governance` |
| Review of governance files | `.github/CODEOWNERS` |
| Dependency updates | `.github/dependabot.yml` |

Commit messages and pull request titles use Conventional Commits and are written in English:
`type(scope): description`, for example `feat(rooms): add room endpoints`.
The hook is installed on the first `dotnet restore` in Debug. Set `HUSKY=0` to skip it.
